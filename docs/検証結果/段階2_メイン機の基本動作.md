試作で分かったこと：

- `static inline` のLVGL関数（例：`lv_layer_top`）は、バインディングに生成されない。代わりに実体のある関数（`lv_disp_get_layer_top`・`lv_disp_get_default`）を呼ぶ。
- 匿名enumの定数は `LV_ALIGN_TOP_LEFT`（型は `_bindgen_ty_N`）の名前で生成される。
- **依存の版を固定しないと、実行時に失敗する**：`esp_lcd_touch_gt911` を `^1` で指定すると1.2.1に解決され、設定マクロが `scl_speed_hz` を設定するため、旧I2Cドライバ（サンプルが使用）で `esp_lcd_new_panel_io_i2c` が `ESP_ERR_INVALID_ARG` を返して起動を繰り返した。サンプル同梱の版（1.1.1~1）に固定して解消した。
- **`idf_component.yml` の変更は、`cargo build` だけでは `esp-idf-sys` の再ビルドを引き起こさない**：変更後は `cargo clean -p esp-idf-sys` で作り直す必要があった。
- 判断：RustからLVGLのUIを作る方式は成立した。要件定義書DEV-03の「画面部分のみC/C++へ切り替える」条件には該当しない。ただし、本実装の画面（4画面のメーター）で、LVGLのAPIをRustの `unsafe` で直接呼ぶ方式で十分か、安全なラッパーを作るかは、段階3で決める。

## CH422Gの出力ビット（公式サンプルのソースから整理）

出力は `0x38` への1バイトの書き込みで設定する（bit n = EXIO n）。`0x24` に `0x01` を書いて出力モードにする。

| ビット | EXIO | 用途 | 根拠（ソース上の値） |
| --- | --- | --- | --- |
| bit1（0x02） | EXIO1 | タッチのリセット（Lowでリセット） | タッチのリセットで `0x2C`（bit1=0）→ `0x2E`（bit1=1） |
| bit2（0x04） | EXIO2 | バックライト（Highでon） | `bl_on`=`0x1E`、`bl_off`=`0x1A`。差が `0x04` |
| bit3（0x08） | EXIO3 | LCDのリセット | 全ての値でHigh |
| bit4（0x10） | EXIO4 | SDのCS（Lowで選択） | `bl_on`の`0x1E`はbit4=1、SDサンプルの`0x0A`・タッチリセットの`0x2E`はbit4=0 |
| bit5（0x20） | EXIO5 | USBの切り替え | タッチリセットの値（`0x2C`・`0x2E`）でHigh |

通常動作の値は `0x2E`。**書き込む値は、ビット単位でまとめて管理する**（一方の操作で他方の状態が変わるため）。

## 実施中に分かったこと

- **サンプルはタッチが無効で配布されている**：`08_lvgl_Porting/main/lvgl_port.h` の `CONFIG_EXAMPLE_LCD_TOUCH_CONTROLLER_GT911` が `0`。`1` に変更して初めてGT911が初期化される（作業用コピーのみ変更）。無効のままでは起動ログに `Initialize touch controller GT911` が出ず、タッチは取得されない。
- **タッチ座標のログ**：サンプルは座標を `ESP_LOGD`（既定では出力されない）で記録している。確認のため作業用コピーで `ESP_LOGW` に変更した。
- **GT911の警告**：`GT911: Unable to initialize the I2C address` が出るが、直後にTouchPad_ID（`0x39,0x31,0x31`）が読め、座標も取得できた。原因は未確認。
- **CH422Gの状態は、ESP32のリセットでは戻らない**：バックライト・タッチのリセット・SDのCSは、I/Oエキスパンダ（CH422G、I2Cアドレス `0x24`・`0x38`）の出力ビットで制御される。`03_SD_Test` は `0x38` に `0x0A` を書き、バックライトが消える（バックライトはbit2で、`0x0A` ではbit2が0。下記「CH422Gの出力ビット」）。その後に `08_lvgl_Porting` を書き込んでも、このサンプルはバックライトをオンにする処理（`wavesahre_rgb_lcd_bl_on`）を呼ばない（`main.c` でコメントアウト）ため、画面が映らなかった。USBの抜き差し（電源の入れ直し）で復帰した。この因果は、ソースと現象からの推定で、CH422Gのレジスタ内容を直接確認したものではない。
- **実装への影響**：バックライト・タッチのリセット・SDのCSが同じCH422Gの出力を共有するため、書き込む値をビット単位でまとめて管理しないと、一方の操作でもう一方の状態が変わる。公式の `wavesahre_rgb_lcd_bl_on()`（`0x1E`）はSD_CSをHighにするため、SDと併用するアプリでは呼ばない。通常動作の値（`0x2E`）を使う。
- **訂正**：本ファイルの初版は、バックライトを「ビット4」と記録していた。ソース上の値（`bl_on`=`0x1E`、`bl_off`=`0x1A`）の差から、正しくはbit2（`0x04`）。結論（SDサンプルがバックライトを消す）は変わらない。
- **SDカードが認識されない事象**：フォーマットなしの実行でFATのマウントに失敗し（`failed to mount card (13)`）、フォーマットを有効にして再実行すると初期化がタイムアウトした（`ESP_ERR_TIMEOUT`）。カードを挿し直すと、マウントとファイル操作に成功した。接触不良が原因だった可能性が高いが、断定はできない。挿し直し後の実行ではフォーマットの警告は出なかったため、カードの中身が消えたかは確認していない。
- **自動フォーマットの扱い**：サンプルは既定ではフォーマットしない（`CONFIG_EXAMPLE_FORMAT_IF_MOUNT_FAILED` は無効）。今回は確認のため、作業用コピーで有効にした。手順書の方針（自動フォーマットを既定にしない）に従い、本実装には持ち込まない。
- **ESP-IDF版**：サンプルはv5.5.2、Rust側（`firmware/main`）はv5.5.3。両者は別のビルドで、版の差による問題は、今回の範囲では出ていない。
